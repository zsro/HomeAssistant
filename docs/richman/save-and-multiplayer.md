## 1. Goal · 目标

玩家能够离开页面后继续同一局，也能够用自己的账号与朋友加入同一房间。恢复后资产、待处理问题、电脑行为和后续随机结果保持一致；联机时所有参与者共享服务器确认的同一进度。复用已经完成的原版风格 UI 和规则，不重新开发一套游戏。

## 2. Scope · 范围

首版包含：账号云存档、手动保存/自动保存、读取与继续、版本不兼容和失败反馈；2–4 个座位的私人房间、现有账号登录、人机混合、准备/开始、实时命令同步、断线重连和服务器重启恢复。

已实现产品默认值：每账号 3 个手动槽、1 个自动槽；自动槽在回合边界及关键决策完成后的稳定点更新并合并短时间内的重复请求。读取后等待玩家点击继续，防止电脑立刻执行。SAVE-02 固定槽位键为 `manual-1`、`manual-2`、`manual-3`、`auto`，不写入规则指纹；SAVE-03 在新局/接受读档后启用稳定点调度，合并至最多每 30 秒一次。

首版不包含：原生 `.sav`、任意历史回放文件导入产品、个人存档转联机、联机任意回滚、公开匹配、观战、聊天、排名及全地图/全角色。旧模式和回放继续可用，但产品存档支持表从 v47 起明确登记，不默认声称所有旧模式可保存。

## 3. Core Gameplay · 核心流程

单机：新建对局 → 正常游戏 → 稳定点保存 → 离开 → 登录后 LOAD/继续游戏 → 校验并恢复 → 确认继续 → 完成原先待处理决策 → 推进后续回合。

联机：创建房间 → 分享房间码 → 各自登录加入 → 选座位/角色并准备 → 房主开始 → 服务器逐条裁决操作 → 所有客户端呈现已确认结果 → 断线玩家重连取回最新进度 → 服务器确认终局并持久化结果。

玩法和胜负沿用当前规则。房主仅有房间组织权限，不能替其他人操作、提交骰子结果、修改资金或覆盖联机历史。

## 5. Interaction Flow · 交互流程

### 单机保存与读取

1. 玩家点击 SAVE，在稳定点捕获同一 revision 的完整封装；若处在动画/小游戏运行阶段，提示等待，不伪造保存成功。可取消待保存请求。
2. 独立于实时游戏状态保留本次不可变请求；保存中即使继续游戏，也明确显示已保存的是哪个回合/revision。自动保存按槽位串行，防止旧请求最后到达反而覆盖新进度。
3. 后端验证身份、格式、规则/地图版本和并发版本，事务写入。只有提交成功才显示保存时间；请求超时以同一 requestId 查询/重试，不能生成重复存档版本。
4. LOAD 先获取并校验候选档，在隔离的新宿主中重建；失败不销毁当前对局。用户确认替换后才释放旧场景、切换游戏和清除旧表单。
5. 从快照推导真实必答窗口，展示“已恢复，点击继续”。恢复屏障只阻止宿主自动推进，不偷偷改引擎的 pause/revision；解除后遵守存档原有暂停状态，需要解除暂停则走原命令。
6. 自动保存失败显示未保存状态和重试；离开前有未保存进度时提供“保存并退出/直接退出/取消”。保存失败不能自动退出。浏览器关闭瞬间不承诺必定完成网络保存。

### 房间与联机

1. 登录创建房间，服务端生成不可轻易枚举的房间码；加入/查找限流。房间码用于邀请，不代替每次操作的账号与成员鉴权。
2. 房主配置 2–4 个座位及电脑；真人一人一座，角色不重复。变更配置撤销受影响的准备状态；开局采用原子状态转换，重复点击只产生一局。
3. 开局冻结座位与规则版本。服务端发送当前用户可见投影、revision、当前应答人与合法操作；客户端准备完资源后进入场景。
4. 玩家提交 commandId、gameId、expectedRevision、decisionId（需要时）及操作参数；身份和 playerId 由服务端账号/座位映射决定。
5. 服务器校验并串行处理，提交事务后返回应答并广播新 revision；客户端更新界面。旧版本、重复包和乱序不能二次结算；必要时重新获取最新快照。
6. 断线客户端立即停止发送操作，显示重连。重连报告上次 revision，服务器补发可用事件或完整投影；缺口无法补齐时直接重同步，不要求重播所有画面。
7. 离线者不参与的决策可以继续；到必须由离线玩家应答的决策时等待。首版不因超时自动花钱、弃权、认输或改为电脑；重连后继续同一问题，其他玩家可返回大厅，房间持久保留。自动托管另立产品规则。
8. 房主在开局后离开不影响服务器权威；等待阶段房主明确离开时按座位顺序优先交给在线真人，无在线成员则交给仍在房间的第一位真人，最后一位离开关闭空房间；单纯断线不移除成员。首版不自动删除进行中的对局。

## 6. States And Feedback · 状态与反馈

| 状态 | 用户反馈 | 处理 |
| --- | --- | --- |
| 空档 / 无房间 | “暂无存档，开始新局” / 创建或加入 | 不展示假的继续按钮 |
| 等待保存点 | “当前动画/小游戏结束后保存” | 不提前写成功；退出/换局取消排队任务 |
| 保存中 / 已保存 | 回合、保存时间、当前保存进度 | 禁止重复覆盖提交；新进度与已保存进度分开 |
| 网络失败 / 登录过期 | “尚未保存，重试” / 重新登录 | 保留当前局和上次成功档，不清空数据 |
| 槽位冲突 | “此存档已在其他页面更新” | 重新读取远端摘要，可选择其他槽；不静默强制覆盖 |
| 损坏 / 版本不支持 | 指明错误类型，可返回列表 | 原文件保留，当前局不变；不猜测兼容后直接读入 |
| 联机连接中 / 断线 | 当前连接状态、重试与等待者 | 只有服务端应答才算操作完成，不做本地资产预结算 |
| 操作过期 / 无权限 | “状态已更新” / “等待某某应答” | 重同步并清理过期输入；不自动重新提交旧决策 |
| 房间恢复中 / 已结束 | 恢复提示 / 最终结果 | 恢复完成前禁用操作；终局禁止写入游戏命令 |

## 7. Rules And Edge Cases · 规则与边界

### 保存边界

稳定点按领域状态和完整待处理决策判断，不能只看 `SessionSnapshot.phase`。允许等待掷骰、岔路选择、静止待应答窗口、回合结束和终局；拍卖/反应/债务/保险/嵌套事件须完整保存上下文，不能绕过它们保存一个虚假的“回合开始”。

首版不保存到掷骰/移动的插值帧或小游戏 `playing` 中途；等待下一个稳定点。小游戏开始前/结果确认可保存。暂停只冻结执行，不把半路移动变成安全保存点。小游戏/魔法等含内部阶段的窗口必须逐状态列入 SAVE-01 白名单，未列入状态明确不可保存。

必须保留 RNG、领域 pending 及 serial、决策 ID、资金/持仓/产权、日期与期限、有限供应池、效果/关系、付款回调链、神仙/道路物件、科研与时光机内部检查点。时光机回退领域世界的既有语义不能替换成整局读档，也不能让联网命令序号倒退。

音量、相机、窗口草稿、DOM 焦点、Pixi 实例和动画毫秒属于表现态，不进入权威规则快照；有需要可独立存偏好。恢复禁止重放历史音频、重复发送动画结束或重复结算小游戏奖励。

### 账号、并发与兼容

服务端从认证上下文取 userId，不能信任请求中的 ownerId；列表/读取/更新都检查所有权。单机客户端产生的档案属于本人可恢复数据，不是可信排行榜成绩，也不能作为联机服务器的权威历史。

槽位版本与游戏 revision 是不同概念：slotVersion 防止多标签/设备覆盖，revision 表示规则进度。读取旧档后形成新的本地分支；再次保存必须基于当前槽位版本显式覆盖或写入其他槽，不能仅比较游戏 revision 大小判断新旧。

格式版本、规则版本、地图指纹、目录/物品规则指纹与资源版本分别校验。纯图片更新不默认破坏规则档案；逻辑内容变化须明确兼容表或迁移。未知新版本拒绝读取；迁移生成新版本并保留原档，不能静默丢字段。

### 联机特别边界

- 操作者由实际待应答决策确定，不能只认 `active`。竞价人、反应者、实际付款人、认输选人及嵌套保险等逐项覆盖。
- 服务端只允许外部玩家命令白名单；`animationDone`、小游戏 tick、AI、内部结算由服务端宿主产生，不能让客户端声称“动画结束”来加速。
- 客户端不得直接收到完整内部 `GameState`；RNG、牌池顺序、未来事件等按规则分级投影。不能因现有本地快照包含数据就把它广播给所有玩家。
- 同一账号多连接默认仅最新连接可操作，旧连接只读并提示；使用连接代次校验，旧包不能在重连后冒用席位。
- 单机暂停保持现状；联机菜单仅在本机打开，不冻结全局或暂停服务器时钟。多人同意暂停暂未开放，后续独立定义全员同意及恢复协议；NET-01 拒绝客户端 `pause`，不允许一人直接冻结全局。离线真人应答不自动托管。
- 小游戏首版仍由服务端持有时钟和合法输入窗口，客户端只上报动作、不上报分数；记录服务端接受的输入顺序、频率与 tick。时钟和输入排序会影响结果，必须在 NET-01 先做端到端可玩性验证，未通过不能宣称当前完整规则已支持联机。

## 8. Data And Technical Notes · 数据与实现落点

### 已有基础与缺口

`GameEngine` 已有 `gameId/expectedRevision/playerId/action`、命令去重、确定性随机数和 `replayGame`。它的私有 `accepted/commands/log` 不在 `GameState` 内；`GameSession` 另有 `commandSerial`、电脑策略配置和 `researchMemory`。`SessionSnapshot` 是展示投影，不能直接成为存档格式。

单机 AI、动画完成、小游戏 tick 继续由浏览器 `GameSession.tick` 推进；NET-01 对局改由 `GameHost` 服务端推进，两种会话不能同时拥有同一联机局。个人存档恢复 Worker 只校验档案。后端另有持续运行的 NET 宿主，NET-02 已接房间与正式网络会话 UI；存档、对局路由各自鉴权及解析，先于全局 32 KB 解析器挂载。

### SAVE-01：已实现的封装和恢复路径

实现入口：[save.ts](../../shared/richman/game/save.ts)、[命令校验](../../shared/richman/game/save-validation.ts)、[GameSession](../../frontend/src/features/richman/game/session.ts)。纯核心于 NET-01 迁至 shared，旧路径保留兼容导出。仅支持 `surrender` / v47；旧版本回放验证继续保留，不开放旧版本产品存档。

- `session.saveAvailability` 返回稳定点状态；`await session.exportSave()` 返回独立 JSON 字符串，在第一次异步等待前捕获同一 revision 的引擎、命令与控制配置。
- `await GameSession.restore(manifest, json)` 在新宿主中重建，成功前不触碰原局；不调用 `start()`、生成 ID/种子、播放历史声音或执行 AI。
- 新会话 `state.restorationPending` 为 true；`continueRestored()` 仅移除宿主屏障，不改变领域 pause、revision 或 RNG。原来已暂停的局仍需正常解除暂停。
- `parseSave` 只做结构检查；`restoreSave` 再执行兼容性、逐命令合法性、稳定点与摘要验证。后端不能把仅通过 `parseSave` 当成完整验证。
- 规则状态、完整事件日志和去重集合由回放重建；科研记忆逐命令重建。命令计数包含被拒绝操作留下的空号，后续编号不碰撞。近期展示日志、音频队列、动画插值和电脑等待时间重新初始化。

`SaveEnvelopeV1` 实际字段：

| 字段 | 职责 |
| --- | --- |
| `formatVersion: 1`、`sessionVersion: 1` | 格式与宿主协议独立版本 |
| `mapId: japan`、`assetVersion` | 当前地图标识；assetVersion 记录 manifest.version，纯表现版本变化不作为拒绝读档的条件 |
| `gameId`、`revision` | 与 replay.config 和完整命令数交叉校验 |
| `replay` | 既有 Replay v1：规则 ID、地图/地产目录/物品指纹、开局配置和全部已接受命令 |
| `session` | mode、computerIds、computerPolicy、commandSerial；与开局人类座位交叉校验 |
| `stateDigest` | 对规范化领域状态、重建科研记忆及 session 配置计算 SHA-256；不作为防作弊签名 |

开局参数直接使用 replay.config，不重复存一份 SessionOptions；读取时重建 SessionOptions。savedAt、槽位版本及列表摘要由 SAVE-02 后端包装，当前恢复契约不伪造服务端时间。

实现先用 `replayGame` 的空命令路径核验开局及指纹，再逐命令执行；research-v1 同步调用 `observeResearch`。完整恢复不能直接用现有 `replayGame` 的最终引擎替代，它不会恢复宿主科研记忆。

当前白名单允许 idle/turnEnd/finished、岔路及现有静止待应答窗口；魔法 draw/choose/result/build、小游戏 ready/result 明确允许，playing 禁止；保险 pending 使用 commerce phase。rolling/moving 即使暂停仍不可保存。拒绝保存时返回可解释原因；SAVE-03 已接等待下一稳定点和可取消的排队保存。

默认限制为 UTF-8 **8 MiB、20,000 条命令、恢复预算 30 秒**，每 32 条命令让出事件循环（SAVE-03 调整，便于取消与绘制进度）。结构、未知字段/动作、非法座位、过期 revision、重复/倒退序号、坏指纹和损坏摘要均拒绝。预算按实际运行时间检查，不是所有 20,000 条命令都能在任意设备上完成的承诺；SAVE-02 已增加服务端 Worker、并发准入和硬超时；浏览器已有 SAVE-03 的进度、取消及错误反馈。

2026-10-20 验证：[机器结果](save-01-results.json)。四份既有 v47 浏览器导出共 4,990 条命令，16 个稳定前缀恢复后执行完整后缀，逐项比较领域状态、事件、RNG、科研记忆及下一策略选择。覆盖非当前玩家竞价、认输、日期结算、保险、魔法、小游戏边界、反应、时光机和终局。为检验非空记忆，使用明确标记的 research-v1 宿主变体；不声称原浏览器都用了该策略。另以合法命令生成三人债务局，在第 1,398 条保存，再验证 40 条后续命令及处置；没有直接注入状态，不是新增浏览器验收。

实测最大档案 455,316 字节（2,442 条命令），解析约 3.49 ms、完整恢复约 11.24 秒；三人债务档 193,571 字节，恢复约 1.69 秒。环境为本机 macOS arm64 / Node 23.11.0，可能同时运行构建或测试；这些是观测值，不是生产或移动设备保证。该测量是 SAVE-01 历史基线。SAVE-02 的 Node Worker、云主机测量和请求预算见下节；SAVE-03 已提供恢复中与超时反馈。

### SAVE-02：MySQL 与 API（已实现）

实现入口：[路由](../../src/modules/richman/save-routes.ts)、[事务服务](../../src/modules/richman/save-service.ts)、[隔离校验](../../src/modules/richman/save-validator.ts)、[Worker](../../workers/richman-save.ts)、[迁移](../../database/migrations/202610200001-richman-saves.ts)。复用 Express、Sequelize 和 Bearer 账号鉴权，所有 owner 均来自认证上下文；客户端不能提交 ownerId。

| 接口 | 请求 / 返回 |
| --- | --- |
| `GET /api/v1/richman/saves` | `data.saves` 为本人已保存槽位的摘要数组，空槽省略，不读取完整 payload |
| `GET /api/v1/richman/saves/:slot` | 本人当前成功版本的回执 + `save` 原始 JSON 字符串；空槽返回 404，不透露其他账号 |
| `PUT /api/v1/richman/saves/:slot` | 严格接收 `{requestId, expectedSlotVersion, save}`；`save` 是 SAVE-01 `exportSave()` 的原始返回值。成功统一 200 |

`slot` 固定为 `manual-1/manual-2/manual-3/auto`。`requestId` 为 1–64 位字母、数字、下划线或连字符，建议 UUID；`expectedSlotVersion` 首次为 0，覆盖使用最新服务端槽位版本。回执含 `slot/slotVersion/revisionId/savedAt/bytes/summary`；summary 由恢复后的状态生成，含 gameId、游戏 revision、规则、地图、角色/电脑座位、日期、turn、当前玩家、暂停、phase 和 stateDigest。时间使用服务端 UTC；所有成功读写响应 `Cache-Control: no-store`。完整机器协议见[OpenAPI 定义](../../src/modules/richman/save-openapi.ts)，运行时 `/api/docs`。

`richman_save_slots` 主键为 `(owner_id, slot_key)`，保存槽位版本和当前 revision 指针；`richman_save_revisions` 以 UUID 为主键，保存 MEDIUMTEXT 原档、摘要 JSON、字节数、请求摘要、服务端时间。另设 `(owner_id, slot_key, request_id)` 与 `(owner_id, slot_key, slot_version)` 唯一约束。用户外键及当前版本引用使用 RESTRICT，避免删除用户或版本时静默丢档。应用只插入 revision，不修改旧档；首版保留全部成功历史，无自动清理和删档接口。

写入先查历史 requestId，再在 Worker 中完整恢复。成功后开启 READ COMMITTED 事务，锁定已有用户行以串行化首次建槽和后续覆盖，同时复核账号状态/authVersion；再次检查幂等记录和槽位版本，插入不可变版本，再创建槽位或以旧版本条件更新指针。恢复期间不持有数据库锁。插入/指针更新失败整体回滚，旧档保留；提交应答丢失时以原请求重试查询已提交记录。

幂等摘要是 `SHA256(expectedSlotVersion + "\n" + save原始UTF-8字节)`，作用域为本人/槽位/requestId。同一请求即使当前槽位已推进也返回原成功回执；JSON 字符串空白或 expectedSlotVersion 改动均算不同载荷，返回 `409 SAVE_REQUEST_REUSED`。不同请求的过期版本返回 `409 SAVE_VERSION_CONFLICT`，details 带当前槽位版本。允许游戏 revision 倒退的显式覆盖，不将它与 slotVersion 比大小。

#### 容量、恢复与错误

- 原档 UTF-8 最大 8 MiB，完整 HTTP JSON 最大 9 MiB（外层字符串转义也计入）；最多 20,000 条命令，完整恢复预算 30 秒。只接收未压缩 `application/json`；这些是多个独立上限，不承诺任何 20,000 条历史都能在预算内恢复。
- 每账号每分钟最多 12 次 PUT；每账号同时 1 次，每个应用实例同时最多 4 个上传/写入请求。Worker 同时最多 2 个，无等待队列，每个 V8 old-generation 上限 256 MiB。当前 PM2 为单实例；未来多实例需要共享限流/调度，不能把进程内配额当成全局配额。
- 父线程硬计时并终止超时 Worker；客户端连接中断也终止尚在执行的恢复。CPU 工作隔离，超时/断线不入库；如果断线时已经进入事务，提交仍可能成功，重试须保持原 requestId/载荷。容量在 Worker 真正退出后才释放。
- Worker 使用受控日本节点和四名角色，执行同一 `restoreSave`，验证指纹、合法命令、稳定点、重建记忆与摘要。`assetVersion` 仅作表现版本记录；不信任客户端提供的替代地图或最终状态。个人存档可恢复不等于联机防作弊认证。
- `401 ACCESS_TOKEN_INVALID` 要重新登录；`404 SAVE_NOT_FOUND` 为空槽；`413 SAVE_TOO_LARGE/PAYLOAD_TOO_LARGE` 为大小限制；`422 SAVE_INVALID` 的 details.reason 沿用恢复契约错误，硬超时为 `SAVE_RESTORE_TIMEOUT`；`429 SAVE_RATE_LIMITED` 及 `503 SAVE_BUSY/SAVE_VALIDATOR_FAILED/SAVE_STORAGE_FAILED` 稍后以原请求重试。数据库错误不把包含完整存档的 SQL 写入通用错误日志。

构建使用[独立后端 Worker 编译配置](../../tsconfig.save-worker.json)，仅编译已有纯规则及 JSON 依赖，未复制规则实现、修改规则指纹，也不需要前端依赖、Pixi 或 Vite。配置沿用规则源代码现有 strict 选项；主后端继续启用 noUncheckedIndexedAccess/exactOptionalPropertyTypes。`npm run build` 同时输出后端与 Worker；`npm run dev` 的 predev 构建 Worker，修改规则后重启该命令。线上执行编译后的 JS，不依赖 tsx。

云主机长局测量发现逐命令复制两份世界状态的额外成本；恢复路径现仅在 v47 科研记忆实际可能变化的 roll/item-confirm 上捕获观测状态。普通移动/动画仍逐命令执行；遇到未经审核的新 rolled 来源拒绝恢复。规则状态、RNG、事件、科研记忆及摘要不变，完整历史后缀对照作为回归门槛。同一份 455,316 字节 / 2,442 命令档案在云主机 Node 20.20.0 / Linux x64 恢复约 **13.49 秒**，主线程 20 ms 定时器最大额外延迟约 **11 ms**；这是单次隔离测量，不是并发负载保证。44 项后端/云数据库检查与 47 项恢复回归通过，前后端构建和本次改动 lint 通过；全仓根 lint 仍有历史 CommonJS/浏览器脚本配置错误。详细结果见[机器结果](save-02-results.json)。

#### HTTP 边界与安全投影

| 接口 | 行为 |
| --- | --- |
| `GET /api/v1/richman/games/:id` | 本人参与对局的完整安全投影；不存在/非成员均 404 |
| `POST /api/v1/richman/games/:id/commands` | `{id, expectedRevision, action}`；成功回执 `{id, gameId, revision, acceptedAt}` |
| `POST /api/v1/richman/games/:id/disconnect` | 移除本人的临时在线租期 |

#### 事务、重试和重启

新增 `richman_games`（当前 revision/状态/检查点 MEDIUMTEXT/SHA256）、`richman_game_seats`（game/player/account/角色/策略）和 `richman_game_commands`（game/revision/原始内部命令/事件/请求摘要/回执）。InnoDB 外键 RESTRICT；每局 revision、每局账号请求 ID、座位账号/角色有唯一约束。每次成功命令或内部 pulse 批次同时更新检查点和完整日志，因此重启直接恢复最新已提交检查点，当前无需重放日志后缀。

1. 每局串行队列上限 8、全局 64；先检查账号座位和持久请求 ID。同一 game/user/id 的规范 JSON 摘要相同，返回原回执，即使 revision 已推进；不同载荷返回 `409 NET_REQUEST_REUSED`。
2. 在隔离候选宿主执行；READ COMMITTED 事务再次锁账号并验证 status/authVersion，锁对局并比较 revision，插入命令/事件/回执及新检查点。提交后才替换可读内存状态。
3. 写入失败整体回滚；提交应答不确定时丢弃缓存，返回 `503 NET_STORAGE_FAILED`。客户端保留原请求重试；后台下次 pulse 也从 MySQL 重建，不能盲目再次掷骰或结算。
4. 检查点包括规则全状态、版本/内容指纹、累计事件序号、座位、科研记忆和宿主逻辑时钟。校验 SHA256、gameId、revision、状态和独立座位表，不兼容或损坏则停止推进。此格式仅服务端可信数据，不接受客户端上传；完整回放应从持久日志重建，不能把检查点后缀冒充完整回放。
5. 引擎生成命令编号随 revision 增长；事件序号和效果边界随检查点累计，时光机回退世界不倒退网络序号。去重及原回执以持久命令表为准，不能依赖引擎恢复后重新开始的短期去重集合。

启动持有独立 MySQL 连接的 `GET_LOCK(<数据库>:richman-host-v1)`，每次命令/pulse 核验调度权；锁断开则 readiness 不可用，不继续写入。PM2 保持单实例；第二个宿主启动被拒绝并释放连接池。最多 32 个活动局，检查点最多 8 MiB；这只是准入上限，不是 32 局实时负载承诺。单局请求队列满延后该局 pulse，不停掉全部游戏。坏检查点导致启动失败；运行中规则故障停止该局并返回 hostError，需要排查后重启，当前无在线修复工具。

### NET-02 实现：私人房间与正式网络会话（2026-10-20）

**页面与流程。** 主菜单/顶栏独立 Web 入口 → 私人房间列表 `/modules/richman/online` → 创建或输入 12 位房间码 → 选角/座位/准备 → 房主开局 → 原版地图及业务窗口。创建默认一位房主、一空位和两关闭座位；最多四座，角色不可重复。未占座位可改为等待真人、科研策略电脑或关闭；资金沿用规则支持的六档，默认 100,000。修改配置、角色或加入/离开均取消全部准备。所有真人在线且准备、无未填空位、至少两位真人/电脑才可开局。开局时间固定 1998-01-01，种子由服务端生成。

**持久化与权限。** 新增迁移 `202610200003-richman-rooms`：房间、四个固定座位及 game seat 的控制窗口 ID；不修改已应用的旧迁移。建房请求自带 UUID，重试返回原房间；房间码使用服务端 48 位随机数，加入/创建每账号每分钟共 10 次，房间请求每分钟 180 次。成员操作使用已认证账号，不接受代填 userId。账号锁防止同时加入多个待开局房间；room revision + 行锁拒绝旧配置上的操作。预开局房主明确离开时优先移交在线成员，按座位顺序选择；无人则关闭房间，单纯掉线保留成员等待返回。开局后座位/配置冻结，退出页面不移除账号座位或停止游戏。

`GameService.provision` 把房间开始检查、初始 game/checkpoint、game seats 和 room.gameId 放进同一事务；提交前不发布缓存。全局创建队列及数据库活动局计数限制 32 局；重复开局返回同一 gameId。创建/开始应答丢失时，可从本人房间列表恢复，不新造同一局。只访问本人参加的房间，房间列表优先显示待开局/进行中的房间，最多 50 条；结束命令同时把关联房间标记为已完成。

**传输与表现。** 正式客户端使用鉴权 HTTP 意图 POST 与单路轮询，通常 400 ms，小游戏 100 ms；不重叠轮询。房间 1.5 s 更新。`NetworkSession` 不创建 `GameEngine` 或 `GameSession`，tick 只做地图插值；小游戏 tick、AI 和 RNG 保持服务端所有。`SceneSession` 允许原场景接入两类会话；既有地图、银行、道具、拍卖、反应、魔法、小游戏等窗口复用。网络状态同时放在顶栏和决策弹窗内，避免必答弹窗挡住重连/重试按钮；等待别人时不弹空的必答窗。网络中的菜单不冻结全局，SAVE/LOAD 明确解释服务器持续保存，不能用个人云档覆盖联机局。共同暂停尚未实现。

**投影和私有信息。** `network-presentation.ts` 明确挑选公开地图、状态、行情、公司账本和展示字段；本人库存/点数/持仓只给本人，其他座位在适配层的空占位不能冒充真实财务信息。库存目标预览仅向本人当前可用道具提供；抢夺目标物品只在实际使用抢夺卡时提供。反应仅发送显示用说明字段，客户端组装现有窗口所需的展示结构，服务器内部接续对象不直接传输。原始 GameState、随机状态、种子、未来牌序、科研记忆、G7 世界、企鹅隐藏宝物均不下发；投影不能用作恢复检查点。场景保持现有图像；尚无网络安全事件流，因此不虚构逐动作声音或历史回执。

**确认、刷新与窗口接管。** 命令包含固定 UUID、原 expectedRevision 和动作，发送前写入按账号/gameId 隔离的 sessionStorage；发送期间锁定再次提交，不乐观扣款。未知结果保留原请求并显示重试，确认或确定拒绝后清除；刷新后仍可重试原请求。若浏览器禁止会话存储则拒绝新操作并提示，避免失去去重编号。HTTP 超时默认 10 秒，重连仍取完整当前投影。每个窗口 claim 一个控制 ID，持久保存在 game seat；最新 claim 可提交，旧窗口只读，需明确点击接管。刷新和重新登录仍绑定原账号；退出时先排空进行中的轮询，再按控制 ID 断开，旧窗口不能清掉新窗口在线状态。

**已执行与边界。** [NET-02 机器结果](net-02-results.json)记录两独立 Chrome 登录、私人房间、真实回合/地产、丢应答去重、房主退出、竞价/反应/射气球、窗口接管和 390 px 房间布局。竞价用四座合法回放前缀进入，只有两个客户端操作；反应和小游戏来自两人合法前缀。不是四个独立玩家完整对局，也不是公网或手机真机验收。NET-03 的断线/重启恢复和人数恢复矩阵见下节；多人长局、公网/真机、负载及共同暂停另列后续验收。数据库迁移仅应用云测试库，生产、Git 提交与 release 包均未更新。

### NET-03 实现：完整断线 / 重启恢复（2026-10-20）

**恢复流程。** 已载入对局在断网或服务器不可用时保留最后确认的画面并禁用业务输入；单路轮询退避到 1/2/4/8/10 秒，网络恢复或页面重新可见时立即尝试。恢复只读取服务器当前局面，不能从旧客户端快照覆盖。首次连接失败保留重新加载和原账号登录入口；已进入的对局支持原地重登。普通重连不抢占控制权；只有进入新窗口或明确点击接管才 claim。所有网络请求（包括带外部取消信号的请求）都受 10 秒上限约束。

**未确认操作。** 发送前将原始 UUID、expectedRevision 和 action 写入按账号/gameId 隔离的 localStorage；兼容迁移 NET-02 的 sessionStorage 记录，因此刷新和正常浏览器重开可保留。禁止存储或恢复记录无法解析时拒绝新的操作并提示；服务器仍保留已经提交的进度。浏览器清除网站数据/无痕窗口关闭会丢失本机未提交意图，但不会删除服务器对局。

新增鉴权 `POST /api/v1/richman/games/:id/recover`，请求 `{pending: 原意图}`。与命令共享单局串行队列，检查成员身份，以 game/account/requestId 查持久回执并校验规范 JSON 摘要，同时返回最新安全投影：

| 结果 | 客户端行为 |
| --- | --- |
| committed | 只有当前投影 revision 不小于回执 revision 才解除待确认；不再次执行操作 |
| missing | 保留原请求并展示“重试原请求”；重连不自动补交消费或旧决策 |
| conflict | 提示编号载荷不一致，清理本机旧意图，按服务器局面重新选择 |
| 断网 / 401 / 503 / 接管冲突 | 保留原请求；重连、原账号登录或明确接管后再核对 |

普通命令 POST 成功也必须经此同步屏障才解锁输入；发送前已经在途的轮询不能充当确认。确定的业务拒绝清理旧意图后仍要取得新的投影；网络未知结果不能解释成未提交。恢复查询只读回执，不消费 RNG、不扣款、不推进决策；同账号旧窗口可查询本人回执，但不能提交命令或续上在线租约。

**旧窗口和迟到包。** 退出会取消并排空 claim、轮询及命令请求，再调用 disconnect。服务端仅允许当前控制 ID 断开，并将该 ID 替换为随机不可用值；迟到旧查询只读、旧命令拒绝，不能复活已退出的窗口。旧窗口断开不影响后来接管的窗口。客户端已销毁后禁止再轮询和修改恢复记录；清理 localStorage 前比较原请求 ID，避免删掉另一窗口的新请求。现有 seat.controllerId 已足够持久化此约束，无新增迁移。

**服务重启与时间。** 启动前加载并校验云 MySQL 的当前检查点，取得单宿主锁后才接受请求。检查点/命令/回执仍在同一事务提交；内存丢失不影响 RNG、资产、嵌套决策、AI 记忆或去重历史。重启不重放已提交演出/奖励，也不按停机时长补算。在线租约为内存态，重启后全员离线；只有当前控制窗口成功认证读取或操作才重新在线。另一玩家连接不能使离线真人小游戏恢复计时。

真人离线不托管、不强制出局，在其应答处等待；断开无法送达时最多等待 15 秒租约过期，期间小游戏仍可能正常计时。明确退出或重启则立即离线。动画与 AI 可继续推进到下一真人应答，菜单不暂停全局。没有离线自动归档/删除；进行中局长期保留并计入 32 局准入上限，满额明确拒绝新局。结束局可继续读取，不计活动额度。共同暂停仍不可用，需另行定义参与人、同意/撤回、超时及断线处理，不隐式添加单方暂停。

**验收。** 云库检查包括恢复接口隔离、迟到包、2/3/4 人及人机检查点、三小游戏停钟/一次结算、非当前玩家拍卖和反应接续；前端检查覆盖旧轮询与回执屏障、跨浏览器存储、认证失效、只读窗口及销毁竞争。真实 Chrome 脚本 `scripts/richman/verify-net-recovery.mjs` 使用独立登录和真实后端子进程 `SIGKILL`，覆盖已提交/未提交两种丢应答和重新进入房间。最终执行结果与未覆盖范围见 [NET-03 机器证据](net-03-results.json)。本地开发，未提交、未部署；并未将人数恢复矩阵等同于各人数完整资产长局、公网/真机或 32 局负载验证。
