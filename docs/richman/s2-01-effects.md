## 证据与本地核验

继续使用 `mytbk/rich4` 固定快照 `ec7d70e693059d1e781d9d1cc2ad7f36d360d39e`。没有重新下载，也没有运行 Windows 原版。新增所读源码的路径、哈希与固定版本 URL 均在审计 JSON；参考 EXE 与本地 EXE 不同，仍沿用 A（本地字节）、B（跨版本候选）、C（未知）分级。

- 本地 `rich4.exe` SHA-256 仍为 `110b29f9d2fadcff3836eb69ec380aa264951859c90955da6e11158d2f956a13`。
- 30 张卡片表在文件偏移 `0x7c152`，13 道具表在 `0x7c242`，每条 8 字节。连续四个数值字节逐行匹配，各表均唯一；通过 PE32 节表解析每条名称指针，43 条指针均指向匹配的 Big5 名称。**这证明 ID 顺序、名称、四字节表值的对应，不能证明所有运行行为。**
- 四字节暂名 `rawFields`；参考结构将 +4 标为初始数量/供应数量、+5 为价格，+6/+7 的语义未核实。不能把供应数量当每位玩家的持有数量。
- 商店购买例程用条目 +5 的数值，从玩家 +48 的 uint16 `points` 扣除；不是 +28 现金或 +32 存款。点数初始值、获取、售卖比例和库存池需继续核验。
- 卡片库存 15 格、每种道具最多 9、消耗回补卡片池/前 8 种道具池为 B 级候选。当前内核仅原子地扣本地库存；共享池、购买与初始发放未接入，必须与首批获取渠道一起实现。
- 参考源码含 36 个新闻索引（Data 441–476）和 49 个命运入口；命运入口复用部分图像，不能按图像去重合并事件。85 个映射在本地 MKF 中均有合法目录/数据头及边界，尚未逐一解码或确认内容与效果。

## 通用内核交付

`frontend/src/features/richman/game/effects.ts` 提供 registry、空库存状态、选择/确认/取消 reducer 和生命周期 reducer：

- 定义指纹隔离不同目录；状态只有 v1、库存、pending、持续实例和单调边界序号，不持有第二份玩家现金/地产/位置。
- begin 验证时机与数量但不扣物品；confirm 重新验证目标、库存、时机和冲突，一次性返回消耗后的草稿及 intent；cancel 不消费。
- 相同 decisionId 不能再次确认。整条 commandId/revision/gameId 的幂等校验由宿主 GameEngine 承担，不能绕过宿主直接把 UI 请求当内核上下文。
- 同组同目标冲突显式选择 reject/replace/stack；稳定顺序为 priority 升序再创建序号。不是原版全局反制优先级。
- 明确 turnStart/turnEnd/dayStart 与 global/source/target clock。相同边界序号拒绝再次扣时长；效果创建时不扣第一次。source 时钟在来源不再收到边界后不推进，需要死后继续到期的效果应声明 global 或来源退出即 remove。
- `playerEliminated` 边界清空破产玩家库存/未完成选择，移除失效目标效果；来源退出时 keep/remove 按定义。宿主需在判定终局之前执行清理，已 finished 状态拒绝新操作。
- 内核不会直接改钱、变更所有权、位移或抽随机数。具体领域 handler 成功后，宿主才与内核草稿一起提交；域操作失败必须丢弃整个草稿，不能先扣卡后执行。

本轮没有将内核导入运行中的 GameEngine/Session，也没有添加测试用游戏模式或假道具。测试定义均以 `fixture:` 命名，仅存在测试文件。**这是 S2-01 的框架交付边界；正式引擎交易接入与 UI 验收属于 S2-02。**
