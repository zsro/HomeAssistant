## 每组如何执行

1. **合并核验**：先看整组的固定参考入口，建立一张规则矩阵：获取、价格/供应、目标、时机、消耗/取消、资金/产权变化、状态冲突、破产清理。只追踪这一组所需证据，不重扫素材。
2. **共享实现**：先实现本组真实需要的公共能力，再接入各物品；沿用商店、背包、决策令牌、日志、回放、预览/取消界面。不要为每件重复建立同一套基础，也不提前设计无用途的大框架。
3. **组内持续交付**：完成一件继续下一件，直到组内范围完成或有明确外部阻碍。某件依赖未核实，不编造规则，也不让它阻塞组内独立条目；报告实际通过数和具体剩余问题。
4. **集中版本与兼容**：共享一组新规则的开发版本，验收冻结后才作为新基线；正式记录过的旧指纹/回放不覆盖。组内若已冻结可复用回放或对外发布，再有语义变化须升级版本。G1 从新 v7 开始，保留 v6。
5. **集中验收（用户已延期至43项实现后）**：每件有关键规则与合法获取测试，共享边界只测试一次；补组内/跨组组合、过期/重复提交、取消/暂停、破产和精确回放。浏览器执行能覆盖不同交互类型的真实闭环，公用全屏/窄屏/重开/清理检查按组集中做；不必给每件都重复一整场百回合 UI 长局。没有实测的场景不得写成已验收。
6. **一次更新交付文档**：每组维护一份报告/来源清单/验收结果，并更新逐项 43 表及接续卡。新规则来源仍逐项可追溯，但不再每一张卡都新建一套接续流程。

价格、稀有道具获取和卡片槽顺序等不能从其他物品套用。默认商店不是所有物品的合法获取方式；真实未完成条目留待办。有限候选范围必须明确标注，不能算作完整原版支持。

反制基础在 G3 集中建设。G1/G2 核验发现跨组反制依赖时，将触发位置与未支持行为明确登记；当前未开放的反制卡不凭空出现。G3 必须回归并补接此前攻击/财产变更，不能永久遗漏。若某件核心效果本身无法在现有系统成立，则保留未完成，不用“候选版”掩盖空效果。

## G1 的具体起步卡

从 `docs/richman-roadmap.md` 的当前接续卡、`s2-02g-wealth.md` 和 `effects-audit.json` 开始，定位固定参考提交中的五张卡函数与共用地产/玩家选择入口。

- 购地：核验目标地块/产权、价格构成、现金与存款、收款方、余额不足和消费顺序。
- 换地：核验需要选几块、双方产权限制、同一地块/同一业主、建筑和附属状态随谁移动。
- 换屋：区分交换楼级、建筑种类还是整块产权；普通/特殊用地限制及满级/零级边界。
- 转向：核验方向字段、上一路格、岔路和开始移动时机；不能简单反转坐标动画。
- 拆除：核验降一级还是拆空、合法建筑/所有权、零级处理与消耗。

五项一起核验、实现可成立的规则、补齐 UI 和组合验收。普通地产与大型用地范围不猜测；发现依赖时登记到本组报告/G4。G1 已新增 5 项、累计 11/43；以上作为已完成范围保留。G2现亦完成七项，累计18/43。G3～G7现已完成统一验收，见[完成清单](s2-02n-acceptance.md)；下一S2-03，不重做单卡实现。
