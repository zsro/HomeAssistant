## 数据交付与解析方式

- [完整数据审计 JSON](japan-map-audit.json)：110 个节点、49 块普通地产、5 块大型用地、6 家公司、16 个景观；保留记录偏移、原始字节、未解释字段和多路格关联。
- `scripts/richman/audit_map.py`：离线、只读、确定性导出；不修改原文件、网页 manifest 或现有布景。
- `scripts/richman/test_audit_map.py`：格式边界与本地数据回归。

资源头为 10 个 little-endian uint32；五对值分别为数量与表起点。每张表包含不计入数量的 0 号记录，真正的 ID 从 1 开始。**记录偏移 = 表起点 + ID × 记录长度**，不能把 0 号记录算作第一块地。

| 表 | 数量 | 起点（解压资源内） | 记录长度 | 道路关联 |
|---|---:|---:|---:|---|
| nodes | 110 | 40 | 40 | 邻接 ID 位于 +0x18，共 4 个 uint16 |
| lands | 49 | 4480 | 52 | 49 个节点，`kind = 2000 + landId` |
| facilities | 5 | 7080 | 56 | 10 个节点，`kind = 4000 + facilityId` |
| companies | 6 | 7416 | 52 | 11 个节点，`kind = 6000 + companyId` |
| landmarks | 16 | 7780 | 28 | 本轮不假定与道路存在相同编码关系 |

现有 `MapNode.kind` 只是 +0x20 的绑定码，不能同时充当所有事件类型。+0x24 是另一个 uint32，源码用其低 8 位分派经过/停留事件。导出名为 `statusBits` 和 `eventCodeCandidate`，完整值均保留。

### 地图核验结果

- 全部 110 节点从节点 1 可达；没有越界邻接或地产引用；49+5+6 个对象全部有道路关联。
- 本张地图没有非对称邻接边。修正导出器原先“含单向支路”的注释；仍保留原始边方向，不能据此认定其他地图一定双向。
- 38 个节点没有地产绑定，另有 8001、8002 两个未解释绑定码。它们不是普通地产，不将其强行转换为景观 ID。
- 一个对象可以对应多个道路节点。姬路大型用地 1 对应节点 46/47，大型用地 3 对应节点 48/49。两者同名但分别拥有不同基础字段，不能按地名合并。
- 普通地产 49 块以及大型用地 5 块的 +0x19、+0x1a、+0x18 均为 0。结合源码分别对应无主、0 级与基础类型的候选含义；这只证明资源初值，不保证开局逻辑永远不改写它们。
- 现有网页 49 个样例房屋由 `32 + (i % 5)` 轮换选择素材，并非读取初始建筑等级；剩余 12 个是已映射景观对象。S1-03 必须使用真实地产状态绘制。
- 16 个景观中有 4 个空名称记录，不能因为没有名称就视为没有内容。本轮保留全部记录。

## R04：地产、价格、租金和升级

### 已识别的字段冲突

参考仓库 `csrc/land.h` 将普通地产 +0x1c 标为地价、+0x1e 标为建造价；`asm/rich4_map.h` 与 `tools/map_data_parser.c` 的标签相反。

读取实际汇编调用后，**v3.11 的可执行逻辑支持 csrc 的解释**：

- 无主地产购买分支 `loc_0041a013` 使用 `(+0x1c + level × +0x1e) × priceIndex`。
- 自有普通住宅升级分支 `loc_004198b9` 使用 `+0x1e × priceIndex`，扣现金并将 +0x1a 加 1。
- 资产估值函数也加上 +0x1c，并按等级累加 +0x1e。

因此不采用 `asm/rich4_map.h` 的这两个字段标签。导出 JSON 仍使用 `word1c`、`word1e` 原始名称，语义解释保持 B 级，等待本地版本场景核验。

### 源码候选规则与待核实项

| 规则 | 本轮候选结论 | 限制 |
|---|---|---|
| 购买 | 基础地价加已有等级建造费，再乘物价指数；检查现金 | B；特殊状态、机会与买卖后续分支未全覆盖 |

## 临时规则的隔离方式

本轮没有往运行代码加入任何猜测的经济数值。S1-02 建议采用两个明确版本化的规则 profile：

- `prototype-japan-v1`：承接 S0 单骰、岔路和手动体验；不宣称完整原版规则。
- `japan-economy-candidate-v1`：以后启用经济候选规则时逐项写入来源与状态，只有首版所需规则补齐后才允许创建经济对局。

未知值使用 `null`，并给出缺失规则 ID；不把 `null` 转成 0，不以缺省百分比补足。对于明确延后支持的系统，通过能力开关关闭，而不是谎报已经还原。规则 profile 是计划，不是本轮新增的可用功能。

## S1-02 数据结构建议

先实现规则核心与可回放命令，再接入现有页面。建议新增独立 `game/` 目录，`Traversal` 暂时保留原型路径，直到适配层完成后替换。

| 对象 | 必需字段 / 边界 |
|---|---|
| `MapDefinition` | mapId、源数据哈希、nodes、lands、facilities、companies；节点引用 `{kind, id}`，不按名称建立资产 |
| `RuleProfile` | id、version、证据登记、受支持能力、资金配置、计价/移动策略；未知项与已关闭系统分开 |
| `GameState` | schemaVersion、rulesVersion、mapId、随机状态、回合和日期、players、properties、pendingDecision、revision、status |
| `PlayerState` | id、角色、human/AI、当前/上一 nodeId、cash、bank、loan、active/bankrupt、状态效果；不存 Pixi 对象 |
| `PropertyState` | 稳定 ID、ownerPlayerId 或 null、level、类型及效果；多个路格共用一个状态 |
| `PendingDecision` | decisionId、所属回合、playerId、type、合法选项；过期或重复确认不再结算 |
| `Command` | commandId、expectedRevision、操作者、操作及参数；由引擎判定是否合法 |
| `DomainEvent` | 顺序号、回合、来源命令、事实及金额变更；渲染按事件播放 |
| `RenderState` | 路段插值、相机、帧、暂停和全屏；显示状态不拥有第二份经济数据 |

移动协议：引擎确定一次骰子结果 → 为每段合法路段产生移动指令 → 适配层播动画 → 用带唯一 ID 的完成命令提交路格到达 → 引擎只接受一次并处理经过事件 → 有剩余步继续，否则落点。无动画测试适配器也能提交相同完成命令；回调本身不能改钱。暂停冻结推进；重置后旧回调因 gameId/revision 不符被拒绝。

S1-02 最小验收：本地 2–4 人按回合轮换、固定种子可回放、重复及过期命令被拒绝、保留岔路与暂停、将运行状态与显示插值分离。先用纯引擎测试覆盖，再连接 UI；不能在这一步附带编造利息、破产或胜负规则。
